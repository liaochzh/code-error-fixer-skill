# 分层防御（Defense in Depth）

> 何时读：根因已修好，想确认「同类问题不会从另一条路径再犯」；或 bug 由非法数据 / 非法调用引起。

## 原则

单点校验只能证明「这条路走不通」，多点校验才能让 bug **结构上不可能**。
但**顺序不能反**：先修根因，再谈加固 —— 用防御层替代根因修复 = 掩盖。

## 四层

| 层 | 作用 | 例子 |
|---|---|---|
| 1. 入口校验 | 在 API / 边界直接拒绝明显非法输入 | 空字符串、不存在路径、非目录、越界索引 |
| 2. 业务校验 | 保证数据对当前操作有意义 | 未初始化就使用、状态机非法迁移、单位/量纲不一致 |
| 3. 环境守卫 | 在特定上下文里禁止危险操作 | 测试环境禁止写真实库 / 真实目录；CI 禁止发真实请求 |
| 4. 可观测 | 其他层失效时留下取证线索 | 操作前记录入参、cwd、环境、调用栈 |

## 落地步骤

1. 追清数据流：非法值从哪来、经过哪些检查点。
2. 列出所有检查点，标出当前无校验的位置。
3. 每层补一条**最小**校验，抛错信息要含实际值与期望约束。
4. 逐层验证：绕过第 1 层，确认第 2 层能接住；以此类推。

## 不该加防御的情况

- 该状态在当前类型 / 状态机里**不可能出现**，加了只是噪音（会用断言或类型系统解决的，就不写运行期分支）。
- 加校验会掩盖上游本该修的问题（先修上游，再加守卫）。
- 校验分支无法被测试覆盖 —— 要么能测，要么别加。
- 一次性脚本、临时诊断代码（验证完即删，不做加固）。

## 与「最小改动」的关系

- 根因修复本身必须保持最小。
- 防御层是**可选的第二步**，在交付里单独说明（必要时单独一次改动），避免和根因修复混在一起导致无法归因。
